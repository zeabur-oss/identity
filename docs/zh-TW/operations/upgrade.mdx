title: 升級與回復 Zeabur Identity
description: 備份並記錄目前的部署，檢查版本差異後升級 Zeabur Identity，再依資料相容性切回舊版或還原備份。
---

先備份並記錄目前的部署，再檢查版本差異、套用新版設定，確認登入與權限正常。需要回復到舊版時，依資料相容性選擇切回舊映像檔或還原升級前的備份。

### 目前不保證的事

Zeabur Identity 目前是 alpha，不保證能順利升級或回復。資源版本仍是 `v1alpha1`，版本之間沒有轉換機制。發行說明明確承諾前，不要假設升級或降版都能成功。記錄實際執行的完整 commit 與映像檔，不要只記錄會重複使用的 tag，例如 `zeabur-identity:dev`。

`kubectl rollout undo` 只會回復 Pod 範本，不會回復 CRD、使用者、簽署金鑰、Secret、RBAC、Service、Ingress 或 kube-apiserver 的檔案。新版 Zeabur Identity 寫入資料後，不保證舊版能讀取。

Zeabur Identity 只執行一個副本，更新時會替換這個副本，不採滾動更新。升級會短暫中斷服務，當時正在登入的使用者必須重新登入。不要增加副本來掩蓋中斷。

## 各版升級須知

下面每個版本列出升級到該版本前要做的事。如果跳過版本升級，從目前執行的版本讀到目標版本，每一段都要看。最新的版本在最上面。

### v0.1 → v0.2

v0.2 改用 `UpstreamProvider` 物件設定 GitHub 與 Google 登入，不再用伺服器選項，也移除了幾個伺服器選項，並改變已連結帳號的儲存方式。通行密鑰不受影響。

#### 1. 移除 v0.2 沒有的選項

只要設定了下列任何一個選項或對應的 `ZEABUR_IDENTITY_*` 變數，伺服器就不會啟動，記錄會寫出是哪個選項。產生升級檔案時，不要在 `--serve-arg` 放這些選項；如果你自己在 Deployment 的 `args` 或 `env` 加過，也要刪掉：

- `--github-client-id`、`--github-client-secret-file`、`--google-client-id`、`--google-client-secret-file`：改用 `UpstreamProvider` 物件（步驟 3）。
- `--store`：伺服器一律把狀態存在 Kubernetes 物件。
- `--upstream-ca-file`：映像檔內建的 CA 已經信任 GitHub 與 Google。如果叢集要經過會用自己的 CA 重新簽署 TLS 的 Proxy 才連得到它們，把這個 CA 掛載到一個目錄，並在 Deployment 同時設定 `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` 與 `SSL_CERT_DIR=<該目錄>`。
- `--key-rotation-period`、`--key-publish-ahead`、`--key-retain-after`、`--metadata-max-age`、`--worker-threads`、`--key-secret`：伺服器一律使用原本的預設值。

#### 2. 允許連到 Google 的探索網址

如果你使用 Google 登入，而叢集有限制對外連線，還要允許以 HTTPS 連到 `accounts.google.com`。Zeabur Identity 現在每次登入前，都會從 `https://accounts.google.com/.well-known/openid-configuration` 讀取 Google 的端點。

#### 3. 在新的 Deployment 之前建立登入提供者

如果你使用 GitHub 或 Google 登入，請在 **檢查並套用資源清單** 這一步，套用新的 CRD 之後、套用新的資源清單之前做這件事。沒做的話，**Continue with GitHub** 和 **Continue with Google** 按鈕會消失，直到補上為止。

把每個用戶端機密存進 Secret `zeabur-identity-upstream`，索引鍵是 `github` 或 `google`。沿用 v0.1 的用戶端機密即可。沒用到的提供者不用加：

```sh
read -rs GITHUB_SECRET     # paste the GitHub client secret, then Enter
read -rs GOOGLE_SECRET     # paste the Google client secret, then Enter
kubectl -n "$NS" create secret generic zeabur-identity-upstream \
  --from-file=github=<(printf %s "$GITHUB_SECRET") \
  --from-file=google=<(printf %s "$GOOGLE_SECRET")
unset GITHUB_SECRET GOOGLE_SECRET
```

接著用原本傳給 `--github-client-id` 和 `--google-client-id` 的用戶端 ID，為每個提供者各建立一個 `UpstreamProvider`。名稱要維持 `github` 和 `google`：它們是在 GitHub 和 Google 註冊的回呼網址的一部分，這樣回呼網址就不用改。

```sh
GITHUB_CLIENT_ID=Ov23li...                         # not a secret
GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com
kubectl apply -f - <<EOF
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: github, namespace: $NS}
spec: {type: GitHub, clientId: $GITHUB_CLIENT_ID, clientSecretKey: github}
---
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: google, namespace: $NS}
spec:
  type: OpenID
  issuer: https://accounts.google.com
  displayName: Google
  clientId: $GOOGLE_CLIENT_ID
  clientSecretKey: google
EOF
```

#### 4. 留下 v0.1 的 CRD 以備回復

用舊版 `zeabur-identityctl` 把 v0.1 的 CRD 存到升級紀錄裡。回復時會用到，見下文。

```sh
/path/to/old/zeabur-identityctl crds > upgrade-record/crds.before.json
```

#### 第一次啟動時會改的資料

v0.2 啟動時，會把每個已連結的 GitHub 或 Google 帳號，也就是 `type: GitHub` 或 `type: Google` 的 `Credential`，改成 `type: Upstream`，並加上 `provider: github` 或 `provider: google`。名稱、擁有者、標籤和連結的帳號都不變，這些帳號照常登入。你自己為已連結帳號建立的 `Credential`，現在要寫 `type: Upstream` 和 `provider`。

#### 回復到 v0.1

v0.1 讀不了 `type: Upstream` 的 `Credential`，它的 CRD 也不接受。v0.2 的 CRD 只允許從 `GitHub` 或 `Google` 改成 `Upstream`，v0.1 的 CRD 完全不允許修改，所以沒辦法直接把類型改回去。要回到 v0.1，需要 v0.1 的 CRD，也要把每個已連結帳號用舊的類型重新寫入。

依下方 **回復** 的說明還原升級前的備份，這兩件事都會完成。如果要保留升級後的變更，改在 Zeabur Identity 停止的狀態下執行下列指令。透過 `github`、`google` 以外的提供者連結的帳號在 v0.1 沒有對應的形式，會被刪除：

```sh
kubectl -n "$NS" get credentials.identity.zeabur.com -o json | jq '.items |= map(
    select(.spec.type == "Upstream")
    | {apiVersion, kind,
       metadata: (.metadata | {name, namespace, labels, ownerReferences}),
       spec: (.spec | .type = ({github: "GitHub", google: "Google"}[.provider]) | del(.provider))}
    | select(.spec.type != null))' > upgrade-record/credentials.v0.1.json
kubectl -n "$NS" get credentials.identity.zeabur.com -o json \
  | jq -r '.items[] | select(.spec.type == "Upstream") | .metadata.name' \
  | xargs -r kubectl -n "$NS" delete credentials.identity.zeabur.com
kubectl apply --server-side -f upgrade-record/crds.before.json
kubectl create -f upgrade-record/credentials.v0.1.json
```

刪除前先看過 `upgrade-record/credentials.v0.1.json`。之後再換回 v0.1 的映像檔和資源清單，並加回步驟 1 的選項。

## 升級前

<Steps>

<Step>

### 確認緊急入口並備份

確認[不經過 Zeabur Identity 的入口](./emergency-access.mdx)能正常使用，再依[備份與還原](./backup-restore.mdx)建立完整備份。

記錄備份時間。還原這份備份時，你會失去備份之後的資料。

</Step>

<Step>

### 記錄目前的部署

記錄來源 commit、`zeabur-identityctl` 版本，以及安裝時使用的所有選項，包括 Issuer、Namespace、映像檔、每個 `--serve-arg`、`--config-secret` 和所有 overlay。確認每個節點都保留可用的舊映像檔。

執行以下指令，儲存目前的部署資訊。這些檔案必須保密。

```sh
umask 077
NS=zeabur-identity
mkdir -m 0700 upgrade-record
kubectl -n "$NS" get deployment zeabur-identity -o yaml > upgrade-record/deployment.before.yaml
kubectl -n "$NS" get pods -l app.kubernetes.io/name=zeabur-identity \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}{"\t"}{.image}{"\t"}{.imageID}{"\n"}{end}{end}' \
  > upgrade-record/image-identities.before.txt
kubectl -n "$NS" rollout history deployment/zeabur-identity > upgrade-record/rollout-history.before.txt
```

這些檔案只是部署紀錄，不能當作備份。

</Step>

<Step>

### 準備新版映像檔

使用 digest，或指向已知 commit 且不會重複使用的 tag。將映像檔載入所有能執行 Zeabur Identity 的節點。

</Step>

<Step>

### 準備新版資源清單

使用新版 `zeabur-identityctl`，搭配原本的安裝選項，產生新版資源清單並存成檔案，再與目前的部署比較。不要用新版預設值產生資源清單後，就直接用管線送進叢集。

</Step>

<Step>

### 檢查版本差異並試升級

先完成上方 **各版升級須知** 中每個經過的版本要做的事，再閱讀兩個版本之間的發行說明，包括 CRD schema、儲存格式、選項與權杖宣告。

先用備份還原出一份複本，在複本上完整試跑同一套升級流程，也要用既有通行密鑰登入。

</Step>

<Step>

### 決定回復方式

如果無法確認舊版能讀取新版資料，就必須靠還原先前的備份來回復，並接受備份之後的資料損失。

如果資料需要遷移，但沒有遷移方式，就不要升級。

</Step>

</Steps>

## 升級

<Steps>

<Step>

### 產生升級檔案

將前四行換成你的設定值。以下 `manifests` 指令與[在 k3s 上安裝並登入](../get-started/quickstart.mdx)相同，會啟用邀請功能。補上安裝時使用的所有選項。如果原本沒有啟用邀請功能，移除 `--serve-arg=--invitations`。

```sh
NS=zeabur-identity
NEXT_ZEABUR_IDENTITYCTL=/path/to/new/zeabur-identityctl
NEXT_IMAGE=registry.example.test/zeabur-identity@sha256:...   # the new image, by digest
ZEABUR_IDENTITY_ISSUER=https://identity.example.test
"$NEXT_ZEABUR_IDENTITYCTL" crds > upgrade-record/crds.next.json
"$NEXT_ZEABUR_IDENTITYCTL" manifests --issuer "$ZEABUR_IDENTITY_ISSUER" --namespace "$NS" --image "$NEXT_IMAGE" \
  --serve-arg=--invitations > upgrade-record/manifests.next.json
# Leave out the empty signing-key Secret: it's only for new installs.
jq '.items |= map(select(.kind != "Secret"))' upgrade-record/manifests.next.json \
  > upgrade-record/manifests.upgrade.json
```

</Step>

<Step>

### 檢查並套用資源清單

套用前，先閱讀 `upgrade-record/crds.next.json` 與 `upgrade-record/manifests.upgrade.json`。

如果套用時出現衝突，先找出原因，不要加上 `--force-conflicts`。不要為了排除錯誤而刪除並重建 CRD，這會刪除該類型的所有物件。

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply --server-side -f upgrade-record/manifests.upgrade.json
kubectl -n "$NS" rollout status deployment/zeabur-identity --timeout=5m
kubectl -n "$NS" logs deployment/zeabur-identity --tail=200
```

保留 `zeabur-identity` Service、`zeabur-identity-internal-ca` 與 `zeabur-identity-signing-keys`，不要替換。新 Service 不保證沿用原本的 IP，但每個 kube-apiserver 的驗證檔案都固定使用舊 IP。

不要在升級時替換根 CA、變更 Issuer 或刪除工作階段。如果新版確實需要不同的 kube-apiserver 設定，請另外處理這項變更，一次處理一台機器。

</Step>

<Step>

### 確認升級結果

檢查實際執行的映像檔、就緒狀態與日誌，再完成以下驗證：

- 使用既有通行密鑰重新登入。
- 分別試做一項你有權限執行的操作，以及一項你沒有權限執行的操作。
- 確認管理員能正常存取。

Pod 就緒後，登入仍可能失敗，所以上面的驗證都要做完。

</Step>

</Steps>

## 回復

<Steps>

<Step>

### 停止不確定的資料寫入

如果無法確認新版寫入了哪些資料，先停止 Zeabur Identity，不讓新版繼續寫入：

```sh
kubectl -n zeabur-identity scale deployment/zeabur-identity --replicas=0
```

</Step>

<Step>

### 依資料相容性選擇回復方式

#### 舊版能讀取目前的資料

只有在確認舊版能讀取目前資料時，才能切回舊映像檔。

如果只變更映像檔，執行：

```sh
kubectl -n zeabur-identity set image deployment/zeabur-identity zeabur-identity="$PREVIOUS_IMAGE"
```

如果還有其他 Pod 範本變更，先檢查修訂紀錄：

```sh
kubectl rollout history deployment/zeabur-identity --revision=N
```

再回復到指定修訂版本：

```sh
kubectl rollout undo deployment/zeabur-identity --to-revision=N
```

手動回復其他變更，再還原副本數。

#### 無法確認舊版能讀取目前的資料

依[備份與還原](./backup-restore.mdx)的還原流程，還原升級前的備份，搭配舊映像檔、資源清單、CRD 與 Secret。還原期間不要啟動 Zeabur Identity。

你會失去備份之後的所有變更，包括新增的通行密鑰、群組變更、用戶端更新與金鑰輪替。

<Callout type="warn">

還原備份後，工作階段與邀請會回到備份當時的樣子。備份之後才撤銷的工作階段，和已經用掉的邀請，都會回來。重新開放服務前，先刪除這些工作階段與邀請。

</Callout>

不要為了啟動舊版而安裝空的簽署金鑰 Secret、刪除憑證或發出新的設定連結。

</Step>

<Step>

### 確認回復結果並記錄損失

檢查映像檔、就緒狀態與日誌，再重新登入。確認一般使用者與管理員都能正常存取，緊急入口也能正常使用。

記錄還原了哪些內容，以及損失了哪些資料。

</Step>

</Steps>
