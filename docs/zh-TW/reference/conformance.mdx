Zeabur Identity 讓 Kubernetes 的使用者用通行密鑰、密碼或上游帳號登入，再發 token 給 kube-apiserver 驗證。它依循 OAuth 2.0 與 OpenID Connect，也依循 WebAuthn 與 Kubernetes 的 Structured Authentication Configuration。這一頁說明它做到什麼、沒做什麼，以及為什麼。

Zeabur Identity 還沒有取得 OpenID 認證，也還沒有跑過 OpenID Foundation 的測試套件。目前每一項要求都有對應的自動化測試，整體流程則用真實的 k3s 叢集與 Keycloak 驗證。

規格編號放在頁尾的註腳。逐條對照程式碼與測試的清單由維護者在儲存庫的 `docs/internal/conformance.md` 維護。

## 讓 kube-apiserver 能驗證

kube-apiserver 從 Zeabur Identity 的探索文件找到簽章金鑰，再用金鑰驗證每一個 access token。所以這一段的重點是文件與金鑰一定要正確。

- 探索文件同時放在 OpenID Connect 與 OAuth 兩個標準位置，內容相同，`issuer` 一致[^discovery]。
- 簽章只用 ES256 與 RS256，金鑰不重複使用，標頭不接受 `jku`、`x5u` 這類讓攻擊者指定金鑰來源的欄位，也不接受 `none`[^jose]。
- 換金鑰時，新金鑰會先公開一段時間才開始簽章，舊金鑰也會保留一段時間，所以 kube-apiserver 的快取不會因為換金鑰而驗證失敗[^rotation]。
- access token 使用 `at+jwt` 格式，每個資源有自己的 `aud`[^jwt-at]。
- 在 k3s 上，每次 CI 都會執行 `kubectl auth whoami`；RKE2 v1.36.5+rke2r1 則由人工驗證過[^kep]。

## 登入流程

授權碼流程是唯一的登入方式，並加上多項收緊。

- 一律要求 PKCE，而且只接受 S256[^pkce]。
- redirect URI 必須完全相符，只有 loopback 位址的埠號可以不同。授權請求出錯時，不會導回不可信的位址，而是顯示錯誤頁[^redirect]。
- 授權碼只能用一次。如果同一個授權碼被重複使用，它已經發出的 token 會一併撤銷[^code]。
- refresh token 每次使用都會換新。舊的 token 再次出現，就表示被偷了，整個 refresh 家族會被撤銷[^refresh]。
- 授權回應帶有 `iss`，防止混淆攻擊[^iss]。
- 支援 PAR 與 token 撤銷[^par]。
- 每次授權請求都要重新登入，因為沒有單一登入（SSO）工作階段。所以 `max_age` 與 `prompt=login` 本來就會被滿足[^core]。

## 登入方式

登入頁提供通行密鑰、密碼與上游帳號三種方式，一般帳號可以任選。

- 通行密鑰使用 WebAuthn，要求可探索的通行密鑰與使用者驗證（指紋、臉部或 PIN），並支援瀏覽器的自動填入[^webauthn]。
- 密碼登入對不存在的使用者、錯誤的密碼與被封鎖的瀏覽器給同一種回應，錯誤次數依瀏覽器計算。登入時可以要求驗證器 App 的驗證碼，驗證碼與備援碼都只能用一次[^totp]。
- 第一位管理員只能透過一次性的設定連結建立，不存在「第一個來的人成為管理員」。連結用過就失效，也會過期。
- 邀請連結只能用一次，只能給被邀請的那位使用者，服務帳號本身不能建立邀請。
- 設定連結與邀請都綁定使用者的 UID。使用者被刪除再用同名重建，舊連結、舊授權碼與舊 refresh token 都不會套用到新使用者。
- 登入頁沒有 inline 指令碼或樣式，並設定防點擊劫持的標頭，也不會把 token 放進瀏覽器儲存空間[^csp]。

## 帳號、管理員與工作階段

帳號分為管理員與一般帳號，管理員的登入方式由 `admin-sign-in` 設定限制。

- `two-factor`（預設）：管理員用通行密鑰，或用密碼加驗證器 App 的驗證碼或備援碼，或用標示為 `mfa: Enforced` 的 OpenID 提供者登入。
- `any`：管理員與一般帳號相同，不另外限制。
- `passkey`：只能用通行密鑰。
- `device-bound-passkey`：只能用裝置綁定的通行密鑰，同步的通行密鑰無法登入，也無法註冊。
- 未標示 `mfa: Enforced` 的提供者，例如 GitHub 與 Google，管理員無法登入也無法連結。標示是營運者的聲明，Zeabur Identity 不讀取提供者回報的 `amr`。
- 這項限制在登入、換授權碼與每次 refresh 都會重新檢查，所以資格不符的工作階段會在下一次 refresh 時結束。
- 只有管理員的 token 帶有 `admins` 群組，而且壽命較短（5 分鐘，一般帳號為 10 分鐘）。CRD 不允許把 `admins` 寫進 `spec.groups`。
- refresh 閒置 1 小時就結束，多團隊或 `device-bound-passkey` 的管理員則是 15 分鐘，無論如何登入 12 小時後都會結束。這些做法對照 NIST SP 800-63B-4 的 AAL2[^nist]。
- 第一位管理員綁定 `cluster-admin`，不需要再登入一次。refresh 會跟著帳號類型走，一般帳號不會保留管理權限。

## 帳號頁

使用者在 `/account` 管理自己的通行密鑰、密碼與連結的上游帳號。

- 所有讀寫都只限於目前登入的使用者，請求裡的名稱只能在這個範圍內挑選。
- 新增或移除通行密鑰、連結或解除上游帳號之前，必須在五分鐘內用自己的通行密鑰重新驗證一次[^reauth]。
- 變更或移除密碼要輸入目前的密碼，錯誤次數與登入共用同一組限制。變更或移除之後，使用者其他的工作階段都會結束。
- 最後一個登入方式永遠不能移除，即使同時有多個移除請求也一樣。
- 移除通行密鑰時，用它登入過的工作階段與授權都會撤銷。
- 每項變更都會留下稽核日誌與 `User` 上的 `Event`，記錄操作者、憑證、裝置型號、IP 與瀏覽器。
- 帳號頁依 Passkey Endpoints 規格公開 `/.well-known/passkey-endpoints`，讓瀏覽器與密碼管理員找到註冊與管理入口[^passkey-endpoints]。

## 上游登入（GitHub 與 OpenID 提供者）

上游登入只用來登入已經連結好的帳號，不會自動建立使用者。

- 連結只能透過設定連結、邀請，或已登入使用者的帳號頁，而且從帳號頁連結要重新驗證通行密鑰。
- 一個上游帳號不能同時連結給兩位使用者。
- 登入時驗證 `state`、PKCE、`iss`，以及 ID token 的簽章、`iss`、`aud`、`azp`、`exp` 與 `nonce`[^upstream]。
- 提供者的新增、修改、刪除與 client secret 輪替，下一個請求就生效，不需要重啟。刪除提供者不會刪掉已連結的帳號。
- 用真實的 Keycloak 驗證過完整流程：未連結的帳號被拒絕、連結後可登入、解除連結後再次被拒絕。

## 儲存與權限

資料全存在 Kubernetes 的自訂資源，沒有另外的資料庫。

- 所有「只能成功一次」的動作（授權碼、設定連結、refresh 輪替）都靠 Kubernetes 的 `resourceVersion` 做比較並交換。叢集測試用 64 個並行請求，確認只有一個成功。
- 服務帳號的 RBAC 採最小權限：Secret 只能依名稱讀取，不能建立，也沒有 RBAC 相關動詞。
- redirect URI 在 CRD 準入檢查與 `zeabur-identityctl client create` 兩處都會檢查，只接受 `https://` 或帶路徑的 loopback `http://`。
- 用戶端密碼是 256 位元的隨機值，只保存雜湊[^secret]。
- 過期的物件由背景工作清除。

## 沒有做的

- **單一登入工作階段與登出**：沒有 SSO 工作階段，所以沒有 RP-Initiated Logout 與 Back-Channel Logout[^logout]。
- **DPoP**：kube-apiserver 只接受 bearer token，所以沒有意義[^dpop]。
- **Rich Authorization Requests 與 Step-up 驗證**：kube-apiserver 無法處理 `authorization_details`，也不會送出 step-up 的挑戰。管理權限改由獨立的管理員帳號提供，並由 `admin-sign-in` 限制它的登入方式。
- **`ui_locales`**：登入頁依 `Accept-Language` 選語言，不看這個參數。
- **無障礙檢查**：每組顏色的對比度都已計算並符合 WCAG 2.2 AA，但還沒有做自動化的瀏覽器稽核與螢幕閱讀器測試[^wcag]。
- **AAL3 的證明**：`device-bound-passkey` 依據通行密鑰的自我回報判斷是否為裝置綁定，attestation 為 `none`。

## 如何驗證

每一項保證都有測試對應，維護者清單列出每個測試的名稱。測試分三層：

- 單元與整合測試，在每次 CI 執行。
- 叢集測試，使用 k3s `v1.37.2`，在每次 CI 執行。
- 端對端測試，使用 Zeabur Identity 的容器映像檔。含 Keycloak 的版本需要另外的伺服器，用 `scripts/keycloak-e2e.sh` 執行，不在 CI 中。

供應鏈與建置的要求，像是禁止 `unsafe`、只接受 OSI 授權、非 root 且沒有 shell 的映像檔、映像檔簽章與 SBOM，請見[安全性](security.mdx)與[版本發佈](releases.mdx)。設計決策見[架構](architecture.mdx)。
