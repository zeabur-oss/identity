---
title: 升级与回滚 Zeabur Identity
description: 备份并记录当前部署，检查版本差异后升级 Zeabur Identity，并根据数据兼容性回滚到旧版或恢复备份。
---

先备份并记录当前部署，再检查版本差异、应用新版配置并验证登录与权限。需要回滚到旧版时，根据数据兼容性选择切回旧镜像或恢复升级前的备份。

### 目前不保证的事项

资源版本仍是 `v1alpha1`，版本之间没有转换机制。新版可能改变数据的存储方式（见下方的升级须知），所以不要假设任何方向的版本切换一定会成功。记录实际运行的完整 commit 与镜像，不要只记录会重复使用的标签，例如 `zeabur-identity:dev`。

`kubectl rollout undo` 只会回滚 Pod 模板，不会回滚 CRD、用户、签名密钥、Secret、RBAC、Service、Ingress 或 kube-apiserver 的文件。新版 Zeabur Identity 写入数据后，不保证旧版能读取。

Zeabur Identity 运行单个副本，更新时会替换副本，不采用滚动更新。升级会短暂中断服务，当时正在登录的用户必须重新登录。不要增加副本来掩盖中断。

## 各版本升级须知

下面每个版本列出升级到该版本前要做的事。如果跳过版本升级，从当前运行的版本读到目标版本，每一节都要看。最新的版本在最上面。

### v0.2.0 → v0.2.1

v0.2.1 改变了 `UpstreamProvider` 与 `Credential` 的写法。已保存的 `Credential` 不用动；已保存的提供方要用新写法重写一遍，因为只要还有 v0.2.0 写法的提供方，服务器就不会启动。

#### 1. 检查 Secret 的键

v0.2.1 不再有 `clientSecretKey`，改为从 Secret `zeabur-identity-upstream` 中与提供方同名的键读取客户端密钥。如果某个提供方的 `clientSecretKey` 与名称不同，在 Secret 中用名称再存一份：

```sh
kubectl -n "$NS" get upstreamproviders.identity.zeabur.com \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.clientSecretKey}{"\n"}{end}'
```

#### 2. 保存提供方与 v0.2.0 的 CRD

在应用新的 CRD 之前完成。应用之后，API 服务器会丢弃 v0.2.1 没有的字段，旧的值就读不到了。

```sh
kubectl -n "$NS" get upstreamproviders.identity.zeabur.com -o json \
  | jq '.items |= map({apiVersion, kind, metadata: (.metadata | {name, namespace, labels}), spec})' \
  > upgrade-record/upstreamproviders.before.json
jq '.items |= map(.spec |= ({clientId} + if .type == "GitHub" then {github: {}}
      else {openid: ({issuer, displayName} + if .scopes then {scopes} else {} end)} end))' \
  upgrade-record/upstreamproviders.before.json > upgrade-record/upstreamproviders.next.json
/path/to/old/zeabur-identityctl crds > upgrade-record/crds.before.json
```

检查过 `upstreamproviders.next.json` 后，在**检查并应用资源清单**这一步，应用新的 CRD 后立即应用它，再应用新的 Deployment：

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply -f upgrade-record/upstreamproviders.next.json
```

#### Credential

不用做任何事。有 `passkey` 的 `Credential` 是通行密钥，有 `external` 的是已关联账号。v0.1 与 v0.2.0 写入的 `type` 和 `provider` 会被忽略。如果你自己的 `Credential` 资源清单写了 `type` 或 `provider`，要删掉才能 `kubectl apply`。

#### 回滚到 v0.2.0

v0.2.0 读取不了没有 `type` 的 `Credential` 和提供方。可以恢复升级前的备份；或在 Zeabur Identity 停止时导出 `Credential`、删除、应用 v0.2.0 的 CRD，再加上 v0.2.0 的类型重新创建。每个已关联账号会对应到 `upstreamproviders.before.json` 中 issuer 相同的提供方。通过升级后才新增的提供方关联的账号没有对应，下列命令会跳过它：

```sh
kubectl -n "$NS" get credentials.identity.zeabur.com -o json \
  | jq --slurpfile p upgrade-record/upstreamproviders.before.json '
    ($p[0].items | map({key: (if .spec.type == "GitHub" then "https://github.com" else .spec.issuer end),
                        value: .metadata.name}) | from_entries) as $provider
    | .items |= map(
        {apiVersion, kind, metadata: (.metadata | {name, namespace, labels, ownerReferences}), spec}
        | if .spec.passkey then .spec.type = "Passkey"
          else .spec.type = "Upstream" | .spec.provider = $provider[.spec.external.issuer] end
        | select(.spec.type == "Passkey" or .spec.provider != null))' \
  > upgrade-record/credentials.v0.2.0.json
kubectl -n "$NS" delete credentials.identity.zeabur.com --all
kubectl -n "$NS" delete upstreamproviders.identity.zeabur.com --all
kubectl apply --server-side -f upgrade-record/crds.before.json
kubectl create -f upgrade-record/credentials.v0.2.0.json
kubectl create -f upgrade-record/upstreamproviders.before.json
```

删除前先检查 `credentials.v0.2.0.json`。`kubectl create` 不会恢复 `status`，所以通行密钥在注册后改过的名称和最后登录时间会丢失。最后换回 v0.2.0 的镜像和资源清单。

### v0.1 → v0.2

从 v0.1 直接升级到 v0.2.1 或更新的版本，跳过上面 v0.2.0 那一节。v0.2 改用 `UpstreamProvider` 对象配置 GitHub 与 Google 登录，不再用服务器选项，同时移除了几个服务器选项。通行密钥和已关联账号无需迁移，照常可用。

#### 1. 移除 v0.2 没有的选项

生成升级文件时，不要在 `--serve-arg` 里放这些选项和对应的 `ZEABUR_IDENTITY_*` 变量；如果你自己在 Deployment 的 `args` 或 `env` 里加过，也要删掉。还留着的选项会让服务器因为不认识这个参数而无法启动：

- `--github-client-id`、`--github-client-secret-file`、`--google-client-id`、`--google-client-secret-file`：改用 `UpstreamProvider` 对象（步骤 3）。
- `--store`：服务器始终把状态存在 Kubernetes 对象中。
- `--upstream-ca-file`：镜像自带的 CA 已经信任 GitHub 与 Google。如果集群要经过会用自己的 CA 重新签发 TLS 的代理才能访问它们，把这个 CA 挂载到一个目录，并在 Deployment 上同时设置 `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` 与 `SSL_CERT_DIR=<该目录>`。
- `--key-rotation-period`、`--key-publish-ahead`、`--key-retain-after`、`--metadata-max-age`、`--worker-threads`、`--key-secret`：服务器始终使用原来的默认值。

#### 2. 允许访问 Google 的发现地址

如果你使用 Google 登录，而集群限制了出站流量，还要允许通过 HTTPS 访问 `accounts.google.com`。Zeabur Identity 现在每次登录前都会从 `https://accounts.google.com/.well-known/openid-configuration` 读取 Google 的端点。

#### 3. 在新的 Deployment 之前创建登录提供方

如果你使用 GitHub 或 Google 登录，请在**检查并应用资源清单**这一步，应用新的 CRD 之后、应用新的资源清单之前完成。补上之前，登录页不会出现 **Continue with GitHub** 和 **Continue with Google** 按钮。

把每个客户端密钥存入 Secret `zeabur-identity-upstream`，键用提供方的名称 `github` 或 `google`。沿用 v0.1 的客户端密钥即可。没用到的提供方不用加：

```sh
read -rs GITHUB_SECRET     # paste the GitHub client secret, then Enter
read -rs GOOGLE_SECRET     # paste the Google client secret, then Enter
kubectl -n "$NS" create secret generic zeabur-identity-upstream \
  --from-file=github=<(printf %s "$GITHUB_SECRET") \
  --from-file=google=<(printf %s "$GOOGLE_SECRET")
unset GITHUB_SECRET GOOGLE_SECRET
```

接着用原来传给 `--github-client-id` 和 `--google-client-id` 的客户端 ID，为每个提供方各创建一个 `UpstreamProvider`。名称要保持 `github` 和 `google`：它们是在 GitHub 和 Google 注册的回调网址的一部分，这样回调网址就不用改。

```sh
GITHUB_CLIENT_ID=Ov23li...                         # not a secret
GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com
kubectl apply -f - <<EOF
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: github, namespace: $NS}
spec: {clientId: $GITHUB_CLIENT_ID, github: {}}
---
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: google, namespace: $NS}
spec:
  clientId: $GOOGLE_CLIENT_ID
  openid: {issuer: https://accounts.google.com, displayName: Google}
EOF
```

#### 4. 保留 v0.1 的 CRD 以备回滚

用旧版 `zeabur-identityctl` 把 v0.1 的 CRD 保存到升级记录中。回滚时会用到，见下文。

```sh
/path/to/old/zeabur-identityctl crds > upgrade-record/crds.before.json
```

#### 已关联账号

不用做任何事。已关联的 GitHub 或 Google 账号，也就是 `type: GitHub` 或 `type: Google` 的 `Credential`，会通过 issuer 相同的提供方登录：`https://github.com` 对应 `github`，`https://accounts.google.com` 对应 `google`。v0.2 不会改动这些对象。

#### 回滚到 v0.1

v0.1 读取不了没有 `type` 的 `Credential`，而 v0.2 写入的 `Credential` 不带 `type`。可以按下方**回滚**的说明恢复升级前的备份；或在 Zeabur Identity 停止时导出 `Credential`、删除、应用 v0.1 的 CRD，再加上 v0.1 的类型重新创建。通过 GitHub、Google 以外的提供方关联的账号在 v0.1 中没有对应的写法，下列命令会跳过它们：

```sh
kubectl -n "$NS" get credentials.identity.zeabur.com -o json | jq '.items |= map(
    {apiVersion, kind, metadata: (.metadata | {name, namespace, labels, ownerReferences}),
     spec: (.spec | del(.provider) | .type = (if .passkey then "Passkey"
       else {"https://github.com": "GitHub", "https://accounts.google.com": "Google"}[.external.issuer] end))}
    | select(.spec.type != null))' > upgrade-record/credentials.v0.1.json
kubectl -n "$NS" delete credentials.identity.zeabur.com --all
kubectl apply --server-side -f upgrade-record/crds.before.json
kubectl create -f upgrade-record/credentials.v0.1.json
```

删除前先检查 `credentials.v0.1.json`。`kubectl create` 不会恢复 `status`，所以通行密钥在注册后改过的名称和最后登录时间会丢失。最后换回 v0.1 的镜像和资源清单，并加回步骤 1 的选项。

## 升级前

<Steps>

<Step>

### 确认紧急入口并备份

确认[绕过 Zeabur Identity 的入口](./emergency-access.mdx)能正常使用，再按[备份与恢复](./backup-restore.mdx)创建完整备份。

记录备份时间。恢复这份备份时，你会丢失备份之后的数据。

</Step>

<Step>

### 记录当前部署

记录源代码 commit、`zeabur-identityctl` 版本，以及安装时使用的所有选项，包括 Issuer、Namespace、镜像、每个 `--serve-arg`、`--config-secret` 和所有 overlay。确保每个节点都保留可用的旧镜像。

执行以下命令，保存当前部署信息。这些文件必须保密。

```sh
umask 077
NS=zeabur-identity
mkdir -m 0700 upgrade-record
kubectl -n "$NS" get deployment zeabur-identity -o yaml > upgrade-record/deployment.before.yaml
kubectl -n "$NS" get pods -l app.kubernetes.io/name=zeabur-identity \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}{"\t"}{.image}{"\t"}{.imageID}{"\n"}{end}{end}' \
  > upgrade-record/image-identities.before.txt
kubectl -n "$NS" rollout history deployment/zeabur-identity > upgrade-record/rollout-history.before.txt
```

这些文件只是部署记录，不能代替备份。

</Step>

<Step>

### 准备新版镜像

使用 digest，或指向已知 commit 且不会重复使用的标签。将镜像加载到所有能运行 Zeabur Identity 的节点。

</Step>

<Step>

### 准备新版资源清单

使用新版 `zeabur-identityctl`，搭配原来的安装选项，将新版资源清单生成到文件，再与当前部署比较。不要将使用新版默认值生成的资源清单直接通过管道传入集群。

</Step>

<Step>

### 检查版本差异并试升级

先完成上方**各版本升级须知**中每个经过的版本要做的事，再阅读两个版本之间的发行说明，包括 CRD schema、存储格式、选项与令牌声明。

先在用备份恢复出的环境上测试完全相同的升级流程，也要使用现有通行密钥登录。

</Step>

<Step>

### 决定回滚方式

如果无法确认旧版能读取新版数据，就必须恢复之前的备份，并接受备份之后的数据损失。

如果数据需要迁移，但没有迁移方法，就不要升级。

</Step>

</Steps>

## 升级

<Steps>

<Step>

### 生成升级文件

将前四行换成你的配置值。以下 `manifests` 命令与[在 k3s 上安装并登录](../get-started/quickstart.mdx)相同，会启用邀请功能。补上安装时使用的所有选项；如果原来没有启用邀请功能，移除 `--serve-arg=--invitations`。

```sh
NS=zeabur-identity
NEXT_ZEABUR_IDENTITYCTL=/path/to/new/zeabur-identityctl
NEXT_IMAGE=registry.example.test/zeabur-identity@sha256:...   # the new image, by digest
ZEABUR_IDENTITY_ISSUER=https://identity.example.test
"$NEXT_ZEABUR_IDENTITYCTL" crds > upgrade-record/crds.next.json
"$NEXT_ZEABUR_IDENTITYCTL" manifests --issuer "$ZEABUR_IDENTITY_ISSUER" --namespace "$NS" --image "$NEXT_IMAGE" \
  --serve-arg=--invitations > upgrade-record/manifests.next.json
# Leave out the empty signing-key Secret: it's only for new installs.
jq '.items |= map(select(.kind != "Secret"))' upgrade-record/manifests.next.json \
  > upgrade-record/manifests.upgrade.json
```

</Step>

<Step>

### 检查并应用资源清单

应用前，阅读 `upgrade-record/crds.next.json` 与 `upgrade-record/manifests.upgrade.json`。

如果应用时出现冲突，先找出原因，不要加上 `--force-conflicts`。不要为了排除错误而删除并重建 CRD，这会删除该类型的所有对象。

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply --server-side -f upgrade-record/manifests.upgrade.json
kubectl -n "$NS" rollout status deployment/zeabur-identity --timeout=5m
kubectl -n "$NS" logs deployment/zeabur-identity --tail=200
```

保留 `zeabur-identity` Service、`zeabur-identity-internal-ca` 与 `zeabur-identity-signing-keys`，不要替换。新 Service 不保证沿用原来的 IP，而每个 kube-apiserver 的认证文件都固定使用旧 IP。

不要在升级时替换根 CA、更改 Issuer 或删除会话。如果新版确实需要不同的 kube-apiserver 配置，将它作为独立变更，一次处理一台机器。

</Step>

<Step>

### 确认升级结果

检查实际运行的镜像、就绪状态与日志，再完成以下验证：

- 使用现有通行密钥重新登录。
- 尝试一项有权限的操作与一项没有权限的操作。
- 确认管理员访问正常。

Pod 就绪后，登录仍可能失败，所以上面的验证都要做完。

</Step>

</Steps>

## 回滚

<Steps>

<Step>

### 停止不确定的数据写入

如果无法确认新版写入了哪些数据，先停止 Zeabur Identity，避免它继续写入：

```sh
kubectl -n zeabur-identity scale deployment/zeabur-identity --replicas=0
```

</Step>

<Step>

### 根据数据兼容性选择回滚方式

#### 旧版能读取当前数据

只有在确认旧版能读取当前数据时，才切回旧镜像。

如果只更改镜像，执行：

```sh
kubectl -n zeabur-identity set image deployment/zeabur-identity zeabur-identity="$PREVIOUS_IMAGE"
```

如果还有其他 Pod 模板变更，先检查修订记录：

```sh
kubectl rollout history deployment/zeabur-identity --revision=N
```

再回滚到指定修订版本：

```sh
kubectl rollout undo deployment/zeabur-identity --to-revision=N
```

手动回滚其他变更，再恢复副本数。

#### 无法确认旧版能读取当前数据

按[备份与恢复](./backup-restore.mdx)的恢复流程，恢复升级前的备份，搭配旧镜像、资源清单、CRD 与 Secret。恢复期间保持 Zeabur Identity 停止。

你会丢失备份之后的所有变更，包括新增的通行密钥、群组变更、客户端更新与密钥轮换。

<Callout type="warn">

恢复备份会带回备份中已撤销的会话与已使用的邀请。重新开放服务前，先删除这些会话与邀请。

</Callout>

不要为了启动旧版而安装空的签名密钥 Secret、删除证书或发出新的配置链接。

</Step>

<Step>

### 确认回滚结果并记录损失

检查镜像、就绪状态与日志，再重新登录。确认普通访问、管理员访问与紧急入口都正常。

记录恢复了哪些内容，以及丢失了哪些数据。

</Step>

</Steps>
