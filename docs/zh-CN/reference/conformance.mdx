---
title: 规范符合度
description: Zeabur Identity 遵循哪些标准、自己增加了哪些保证，以及哪些没有做。
---

Zeabur Identity 让 Kubernetes 的用户用通行密钥、密码或上游账号登录，再签发 token 给 kube-apiserver 验证。它遵循 OAuth 2.0 和 OpenID Connect，也遵循 WebAuthn 和 Kubernetes 的 Structured Authentication Configuration。本页说明它做到了什么、没做什么，以及为什么。

Zeabur Identity 还没有取得 OpenID 认证。OpenID Foundation 的 `oidcc-basic-certification-test-plan` 在 v0.3.4 上运行过一次，但结果不能当作认证：这个计划不发送 `code_challenge`，而 Zeabur Identity 一律要求 PKCE，所以测试使用的是把 PKCE 改为可选的版本。其余失败的用例，来自没有单点登录（SSO）会话，包括已登录时的 `prompt=none`、`id_token_hint` 和 `max_age`。

目前每一项要求都有对应的自动化测试，整体流程则用真实的 k3s 集群和 Keycloak 验证。

规范编号放在页尾的脚注。逐条对照代码与测试的清单由维护者在仓库的 `docs/internal/conformance.md` 维护。

## 让 kube-apiserver 能验证

kube-apiserver 从 Zeabur Identity 的发现文档找到签名密钥，再用密钥验证每一个 access token。所以这一部分的重点是文档和密钥一定要正确。

- 发现文档同时放在 OpenID Connect 和 OAuth 两个标准位置，内容相同，`issuer` 一致[^discovery]。
- 签名只用 ES256 和 RS256，一个密钥只对应一种算法。头部不接受 `jku`、`x5u` 这类让攻击者指定密钥来源的字段，也不接受 `none`[^jose]。
- 换密钥时，新密钥会先公开一段时间才开始签名，旧密钥也会保留一段时间，所以 kube-apiserver 的缓存不会因为换密钥而验证失败[^rotation]。
- access token 使用 `at+jwt` 类型，每个资源有自己的 `aud`[^jwt-at]。
- 在 k3s 上，每次 CI 都会运行 `kubectl auth whoami`；RKE2 v1.36.5+rke2r1 则由人工验证过[^kep]。

## 登录流程

授权码流程是唯一的登录流程，并增加了多项限制。

- 一律要求 PKCE，而且只接受 S256[^pkce]。
- redirect URI 必须完全匹配，只有 loopback 地址的端口可以不同。授权请求出错时，不会跳转到不可信的地址，而是显示错误页[^redirect]。
- 授权码只能用一次。如果同一个授权码被重复使用，它已经签发的 token 会一并撤销[^code]。
- refresh token 每次使用都会换新。旧的 token 再次出现，就说明它被盗了，整个 refresh 家族会被撤销[^refresh]。
- 授权响应带有 `iss`，防止混淆攻击[^iss]。
- 支持 PAR 和 token 撤销[^par]。
- 每次授权请求都要重新登录，因为没有单点登录（SSO）会话。所以 `max_age` 和 `prompt=login` 本来就会被满足[^core]。

## 登录方式

登录页提供通行密钥、密码和上游账号三种方式，普通账号可以任选。

- 通行密钥使用 WebAuthn，要求可发现的通行密钥和用户验证（指纹、面容或 PIN），并支持浏览器的自动填充[^webauthn]。
- 密码登录对不存在的用户、错误的密码和被封锁的浏览器给出同一种响应，错误次数按浏览器计算。登录时可以要求身份验证器应用的验证码，验证码和恢复码都只能用一次[^totp]。
- 第一位管理员只能通过一次性的设置链接创建，不存在“第一个来的人成为管理员”。链接用过就失效，也会过期。
- 邀请链接只能用一次，只能给被邀请的那位用户，服务账号本身不能创建邀请。
- 设置链接和邀请都绑定用户的 UID。用户被删除后用同名重建，旧链接、旧授权码和旧 refresh token 都不会套用到新用户。
- 登录页没有 inline 脚本或样式，并设置了防点击劫持的头部，也不会把 token 放进浏览器存储[^csp]。

## 账号、管理员与会话

账号分为管理员和普通账号，管理员的登录方式由 `admin-sign-in` 设置限制。

- `two-factor`（默认）：管理员用通行密钥，或用密码加身份验证器应用的验证码或恢复码，或用标记为 `mfa: Enforced` 的 OpenID 提供方登录。
- `any`：管理员与普通账号相同，不另外限制。
- `passkey`：只能用通行密钥。
- `device-bound-passkey`：只能用设备绑定的通行密钥，同步的通行密钥无法登录，也无法注册。
- 除了 `any`，没有标记 `mfa: Enforced` 的提供方，例如 GitHub 和 Google，管理员无法登录也无法关联。标记是运维者的声明，Zeabur Identity 不读取提供方报告的 `amr`。
- 这项限制在登录、换授权码和每次 refresh 时都会重新检查，所以资格不符的会话会在下一次 refresh 时结束。
- 只有管理员的 token 带有 `admins` 组，而且寿命更短（5 分钟，普通账号为 10 分钟）。CRD 不允许把 `admins` 写进 `spec.groups`。
- refresh 空闲 1 小时就结束，多团队或 `device-bound-passkey` 的管理员则是 15 分钟，无论如何登录 12 小时后都会结束。这些做法对照 NIST SP 800-63B-4 的 AAL2[^nist]。
- 第一位管理员绑定 `cluster-admin`，不需要再登录一次。refresh 会跟着账号类型走，普通账号不会保留管理权限。

## 账号页

用户在 `/account` 管理自己的通行密钥、密码和已关联的上游账号。

- 所有读写都只限于当前登录的用户，请求里的名称只能在这个范围内选择。
- 添加或移除通行密钥、关联或解除上游账号之前，必须在五分钟内用自己的通行密钥重新验证一次[^reauth]。
- 修改或移除密码要输入当前密码，错误次数与登录共用同一组限制。修改或移除之后，用户其他的会话都会结束。
- 最后一个登录方式永远不能移除，即使同时有多个移除请求也一样。
- 移除通行密钥时，用它登录过的会话和授权都会撤销。
- 每项变更都会留下审计日志和 `User` 上的 `Event`，记录操作者、凭据、设备型号、IP 和浏览器。
- 账号页按 Passkey Endpoints 规范公开 `/.well-known/passkey-endpoints`，让浏览器和密码管理器找到注册与管理入口[^passkey-endpoints]。

## 上游登录（GitHub 与 OpenID 提供方）

上游登录只用来登录已经关联好的账号，不会自动创建用户。

- 关联只能通过设置链接、邀请，或已登录用户的账号页，而且从账号页关联要重新验证通行密钥。
- 一个上游账号不能同时关联给两位用户。
- 登录时验证 `state`、PKCE、`iss`，以及 ID token 的签名、`iss`、`aud`、`azp`、`exp` 和 `nonce`[^upstream]。
- 提供方的新增、修改、删除和 client secret 轮换，下一个请求就生效，不需要重启。删除提供方不会删掉已关联的账号。
- 用真实的 Keycloak 验证过完整流程：未关联的账号被拒绝、关联后可登录、解除关联后再次被拒绝。

## 存储与权限

数据全部存在 Kubernetes 的自定义资源中，没有另外的数据库。

- 所有“只能成功一次”的动作（授权码、设置链接、refresh 轮换）都靠 Kubernetes 的 `resourceVersion` 做比较并交换。集群测试用 64 个并发请求，确认只有一个成功。
- 服务账号的 RBAC 采用最小权限：Secret 只能按名称读取，不能创建，也没有 RBAC 相关动词。
- redirect URI 在 CRD 准入检查和 `zeabur-identityctl client create` 两处都会检查，只接受 `https://` 或带路径的 loopback `http://`。
- 客户端密钥是 256 位的随机值，只保存哈希[^secret]。
- 过期的对象由后台任务清除。

## 没有做的

- **单点登录会话与登出**：没有 SSO 会话，所以没有 RP-Initiated Logout 和 Back-Channel Logout[^logout]。
- **DPoP**：kube-apiserver 只接受 bearer token，所以没有意义[^dpop]。
- **Rich Authorization Requests 与 Step-up 验证**：kube-apiserver 无法处理 `authorization_details`，也不会发出 step-up 的挑战。管理权限改由独立的管理员账号提供，并由 `admin-sign-in` 限制它的登录方式。
- **`ui_locales`**：登录页按 `Accept-Language` 选择语言，不看这个参数。
- **无障碍检查**：每组颜色的对比度都已计算并符合 WCAG 2.2 AA，但还没有做自动化的浏览器审计和屏幕阅读器测试[^wcag]。
- **AAL3 的证明**：`device-bound-passkey` 依据通行密钥的自我报告判断是否为设备绑定，attestation 为 `none`。

## 如何验证

每一项保证都有对应的测试，维护者清单列出每个测试的名称。测试分为三类：

- 单元和集成测试，在每次 CI 中运行。
- 集群测试，使用 k3s `v1.37.2`，在每次 CI 中运行。
- 端到端测试，使用 Zeabur Identity 的容器镜像。含 Keycloak 的测试需要另外的服务器，用 `scripts/keycloak-e2e.sh` 运行，不在 CI 中。

供应链和构建方面的要求，例如禁止 `unsafe`、只接受 OSI 许可证、非 root 且没有 shell 的镜像、镜像签名和 SBOM，请见[安全](security.mdx)和[版本发布](releases.mdx)。设计决策见[架构](architecture.mdx)。
