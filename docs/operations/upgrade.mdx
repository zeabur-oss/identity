---
title: Upgrade and roll back Zeabur Identity
description: Back up and record your current deployment, review version differences, upgrade Zeabur Identity, and use data compatibility to decide whether to roll back to an older version or restore a backup.
---

Back up and record your current deployment, then review version differences, apply the new configuration, and verify sign-in and permissions. If you need to roll back, use data compatibility to decide whether to switch to the old image or restore the pre-upgrade backup.

### Upgrade risks

Resource versions are still `v1alpha1`, and there's no conversion mechanism between versions. A newer version can change how it stores data, as the upgrade notes below list, so don't assume that switching versions in either direction will succeed. Record the full commit and image that's actually running. Don't record only a reusable tag such as `zeabur-identity:dev`.

`kubectl rollout undo` only restores the Pod template. It doesn't restore CRDs, users, signing keys, Secrets, RBAC, Services, Ingresses, or kube-apiserver files. After a newer version of Zeabur Identity writes data, there's no guarantee that an older version can read it.

Zeabur Identity runs a single replica. Updates replace that replica rather than perform a rolling update. An upgrade briefly interrupts service, and users who are signing in at that time must sign in again. Don't add replicas to hide the interruption.

## Upgrade notes

Each version below lists what you must do before you upgrade to it. If you skip versions, read every section from the version you run now to the version you're moving to. The newest version is at the top.

### v0.2.0 → v0.2.1

v0.2.1 changes the form of `UpstreamProvider` and `Credential`. Stored credentials keep working as they are. Stored providers don't: the server doesn't start while a provider in the v0.2.0 form is stored, so write each one again in the new form.

#### 1. Check the Secret's keys

v0.2.1 reads each provider's client secret from the key with the provider's name in the Secret `zeabur-identity-upstream`. `clientSecretKey` is gone. If a provider's `clientSecretKey` differs from its name, add the secret under the name as well:

```sh
kubectl -n "$NS" get upstreamproviders.identity.zeabur.com \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.clientSecretKey}{"\n"}{end}'
```

#### 2. Save the providers and v0.2.0's CRDs

Do this before you apply the new CRDs. After that, the API server drops the fields v0.2.1 doesn't have, and the old values can't be read.

```sh
kubectl -n "$NS" get upstreamproviders.identity.zeabur.com -o json \
  | jq '.items |= map({apiVersion, kind, metadata: (.metadata | {name, namespace, labels}), spec})' \
  > upgrade-record/upstreamproviders.before.json
jq '.items |= map(.spec |= ({clientId} + if .type == "GitHub" then {github: {}}
      else {openid: ({issuer, displayName} + if .scopes then {scopes} else {} end)} end))' \
  upgrade-record/upstreamproviders.before.json > upgrade-record/upstreamproviders.next.json
/path/to/old/zeabur-identityctl crds > upgrade-record/crds.before.json
```

Read `upstreamproviders.next.json`, then apply it right after the new CRDs in the **Review and apply the manifests** step, before the new Deployment:

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply -f upgrade-record/upstreamproviders.next.json
```

#### Credentials

Nothing to do. A `Credential` is a passkey when it has `passkey` and a linked account when it has `external`. The `type` and `provider` fields that v0.1 and v0.2.0 wrote are ignored. A `Credential` manifest of your own that sets `type` or `provider` fails `kubectl apply` until you remove them.

#### Roll back to v0.2.0

v0.2.0 can't read a `Credential` or a provider without `type`. Restore the pre-upgrade backup, or export the credentials, delete them, apply v0.2.0's CRDs and create them again with their v0.2.0 type. Do this with Zeabur Identity stopped. Each linked account gets the provider with its issuer from `upstreamproviders.before.json`. An account linked through a provider added after the upgrade has none, so this leaves it out:

```sh
kubectl -n "$NS" get credentials.identity.zeabur.com -o json \
  | jq --slurpfile p upgrade-record/upstreamproviders.before.json '
    ($p[0].items | map({key: (if .spec.type == "GitHub" then "https://github.com" else .spec.issuer end),
                        value: .metadata.name}) | from_entries) as $provider
    | .items |= map(
        {apiVersion, kind, metadata: (.metadata | {name, namespace, labels, ownerReferences}), spec}
        | if .spec.passkey then .spec.type = "Passkey"
          else .spec.type = "Upstream" | .spec.provider = $provider[.spec.external.issuer] end
        | select(.spec.type == "Passkey" or .spec.provider != null))' \
  > upgrade-record/credentials.v0.2.0.json
kubectl -n "$NS" delete credentials.identity.zeabur.com --all
kubectl -n "$NS" delete upstreamproviders.identity.zeabur.com --all
kubectl apply --server-side -f upgrade-record/crds.before.json
kubectl create -f upgrade-record/credentials.v0.2.0.json
kubectl create -f upgrade-record/upstreamproviders.before.json
```

Read `credentials.v0.2.0.json` before you delete anything. `kubectl create` doesn't restore `status`, so passkeys lose the names users gave them after enrolment and their last sign-in time. Then switch back to the v0.2.0 image and manifests.

### v0.1 → v0.2

Upgrade from v0.1 straight to v0.2.1 or later, and skip the v0.2.0 section above. v0.2 sets up GitHub and Google sign-in with `UpstreamProvider` objects instead of server options and removes several server options. Passkeys and linked accounts keep working without a migration.

#### 1. Remove the options v0.2 doesn't have

Leave these options and their `ZEABUR_IDENTITY_*` variables out of every `--serve-arg` when you generate the upgrade files, and delete any you added to the Deployment's `args` or `env` yourself. An option that is still set stops the server with an unknown-argument error:

- `--github-client-id`, `--github-client-secret-file`, `--google-client-id`, `--google-client-secret-file`: replaced by `UpstreamProvider` objects (step 3).
- `--store`: the server always keeps its state in Kubernetes objects.
- `--upstream-ca-file`: the image's CA bundle already trusts GitHub and Google. If your cluster reaches them through a proxy that re-signs TLS with its own CA, mount that CA into a directory and set both `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` and `SSL_CERT_DIR=<that directory>` on the Deployment.
- `--key-rotation-period`, `--key-publish-ahead`, `--key-retain-after`, `--metadata-max-age`, `--worker-threads`, `--key-secret`: the server always uses the former defaults.

#### 2. Allow Google's discovery address

If you use Google sign-in and your cluster limits outgoing traffic, also allow HTTPS to `accounts.google.com`. Zeabur Identity now reads Google's endpoints from `https://accounts.google.com/.well-known/openid-configuration` before each sign-in.

#### 3. Create the sign-in providers before the new Deployment

If you use GitHub or Google sign-in, do this after you apply the new CRDs and before you apply the new manifests in the **Review and apply the manifests** step. Otherwise the **Continue with GitHub** and **Continue with Google** buttons disappear until you do.

Store each client secret in the Secret `zeabur-identity-upstream`, under the provider's name, `github` or `google`. Use the same client secrets as v0.1. Leave out a provider you don't use:

```sh
read -rs GITHUB_SECRET     # paste the GitHub client secret, then Enter
read -rs GOOGLE_SECRET     # paste the Google client secret, then Enter
kubectl -n "$NS" create secret generic zeabur-identity-upstream \
  --from-file=github=<(printf %s "$GITHUB_SECRET") \
  --from-file=google=<(printf %s "$GOOGLE_SECRET")
unset GITHUB_SECRET GOOGLE_SECRET
```

Then create one `UpstreamProvider` for each, with the client IDs you passed to `--github-client-id` and `--google-client-id`. Keep the names `github` and `google`: they are part of the callback URLs registered at GitHub and Google, so those stay the same.

```sh
GITHUB_CLIENT_ID=Ov23li...                         # not a secret
GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com
kubectl apply -f - <<EOF
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: github, namespace: $NS}
spec: {clientId: $GITHUB_CLIENT_ID, github: {}}
---
apiVersion: identity.zeabur.com/v1alpha1
kind: UpstreamProvider
metadata: {name: google, namespace: $NS}
spec:
  clientId: $GOOGLE_CLIENT_ID
  openid: {issuer: https://accounts.google.com, displayName: Google}
EOF
```

#### 4. Keep v0.1's CRDs for a rollback

Save v0.1's CRDs with the old `zeabur-identityctl` next to your upgrade record. A rollback needs them, see below.

```sh
/path/to/old/zeabur-identityctl crds > upgrade-record/crds.before.json
```

#### Linked accounts

Nothing to do. Each linked GitHub or Google account, a `Credential` with `type: GitHub` or `type: Google`, signs in through the provider with its issuer: `github` for `https://github.com`, `google` for `https://accounts.google.com`. v0.2 doesn't change these objects.

#### Roll back to v0.1

v0.1 can't read a `Credential` without `type`, and v0.2 writes credentials without it. Restore the pre-upgrade backup, as described under **Roll back** below, or export the credentials, delete them, apply the v0.1 CRDs and create them again with their v0.1 type. Do this with Zeabur Identity stopped. Accounts linked through a provider other than GitHub or Google have no v0.1 form, so this leaves them out:

```sh
kubectl -n "$NS" get credentials.identity.zeabur.com -o json | jq '.items |= map(
    {apiVersion, kind, metadata: (.metadata | {name, namespace, labels, ownerReferences}),
     spec: (.spec | del(.provider) | .type = (if .passkey then "Passkey"
       else {"https://github.com": "GitHub", "https://accounts.google.com": "Google"}[.external.issuer] end))}
    | select(.spec.type != null))' > upgrade-record/credentials.v0.1.json
kubectl -n "$NS" delete credentials.identity.zeabur.com --all
kubectl apply --server-side -f upgrade-record/crds.before.json
kubectl create -f upgrade-record/credentials.v0.1.json
```

Read `credentials.v0.1.json` before you delete anything. `kubectl create` doesn't restore `status`, so passkeys lose the names users gave them after enrolment and their last sign-in time. Then switch back to the v0.1 image and manifests, with the options from step 1.

## Before upgrading

<Steps>

<Step>

### Verify emergency access and create a backup

Confirm that [access without Zeabur Identity](./emergency-access.mdx) works, then follow [Backup and restore](./backup-restore.mdx) to create a full backup.

Record the backup time. If you restore this backup, you'll lose all data created after that time.

</Step>

<Step>

### Record the current deployment

Record the source commit, the `zeabur-identityctl` version, and every option you used during installation, including the Issuer, Namespace, image, each `--serve-arg`, `--config-secret`, and all overlays. Keep a usable copy of the old image on every node.

Run the following commands to save the current deployment information. Keep these files confidential.

```sh
umask 077
NS=zeabur-identity
mkdir -m 0700 upgrade-record
kubectl -n "$NS" get deployment zeabur-identity -o yaml > upgrade-record/deployment.before.yaml
kubectl -n "$NS" get pods -l app.kubernetes.io/name=zeabur-identity \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}{"\t"}{.image}{"\t"}{.imageID}{"\n"}{end}{end}' \
  > upgrade-record/image-identities.before.txt
kubectl -n "$NS" rollout history deployment/zeabur-identity > upgrade-record/rollout-history.before.txt
```

These files are deployment records, not backups.

</Step>

<Step>

### Prepare the new image

Use a digest or a non-reusable tag that points to a known commit. Load the image onto every node that can run Zeabur Identity.

</Step>

<Step>

### Prepare the new manifests

Use the new version of `zeabur-identityctl` with your original installation options to generate the new manifests into a file, then compare them with the current deployment. Don't pipe manifests generated with the new defaults directly into the cluster.

</Step>

<Step>

### Review version differences and test the upgrade

Do what **Upgrade notes** above lists for each version you pass. Then read the release notes between the two versions, including the CRD schema, storage format, options, and token claims.

Test the exact upgrade procedure on a restored copy first. Also test signing in with an existing passkey.

</Step>

<Step>

### Choose a rollback method

If you can't confirm that the old version can read the new data, restore the previous backup and accept the loss of data created after the backup.

If the data requires migration and no migration method exists, don't upgrade.

</Step>

</Steps>

## Upgrade

<Steps>

<Step>

### Generate the upgrade files

Replace the first four lines with your settings. The following `manifests` command matches the one in [Install and sign in on k3s](../get-started/quickstart.mdx) and enables invitations. Add every option you used during installation. If you didn't enable invitations in the original installation, remove `--serve-arg=--invitations`.

```sh
NS=zeabur-identity
NEXT_ZEABUR_IDENTITYCTL=/path/to/new/zeabur-identityctl
NEXT_IMAGE=registry.example.test/zeabur-identity@sha256:...   # the new image, by digest
ZEABUR_IDENTITY_ISSUER=https://identity.example.test
"$NEXT_ZEABUR_IDENTITYCTL" crds > upgrade-record/crds.next.json
"$NEXT_ZEABUR_IDENTITYCTL" manifests --issuer "$ZEABUR_IDENTITY_ISSUER" --namespace "$NS" --image "$NEXT_IMAGE" \
  --serve-arg=--invitations > upgrade-record/manifests.next.json
# Leave out the empty signing-key Secret: it's only for new installs.
jq '.items |= map(select(.kind != "Secret"))' upgrade-record/manifests.next.json \
  > upgrade-record/manifests.upgrade.json
```

</Step>

<Step>

### Review and apply the manifests

Read `upgrade-record/crds.next.json` and `upgrade-record/manifests.upgrade.json` before applying them.

If a conflict occurs when you apply the manifests, find the cause first. Don't add `--force-conflicts`. Don't delete and recreate a CRD to resolve an error. That deletes every object of that type.

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply --server-side -f upgrade-record/manifests.upgrade.json
kubectl -n "$NS" rollout status deployment/zeabur-identity --timeout=5m
kubectl -n "$NS" logs deployment/zeabur-identity --tail=200
```

Keep the `zeabur-identity` Service, `zeabur-identity-internal-ca`, and `zeabur-identity-signing-keys`. Don't replace them. A new Service isn't guaranteed to retain the original IP, and every kube-apiserver's authentication file uses the old IP as a fixed value.

Don't replace the root CA, change the Issuer, or delete sessions during an upgrade. If the new version requires different kube-apiserver settings, treat that as a separate change and handle one machine at a time.

</Step>

<Step>

### Verify the upgrade

Check the image that's actually running, readiness, and logs, then complete these checks:

- Sign in again with an existing passkey.
- Attempt one operation you have permission to perform and one you don't.
- Confirm that admin access works.

Sign-in can still fail after the Pod is ready, so complete every check above.

</Step>

</Steps>

## Roll back

<Steps>

<Step>

### Stop writes if the data state is uncertain

If you can't confirm what data the new version has written, stop Zeabur Identity first to prevent further writes:

```sh
kubectl -n zeabur-identity scale deployment/zeabur-identity --replicas=0
```

</Step>

<Step>

### Choose a rollback method based on data compatibility

#### The old version can read the current data

Switch to the old image only after you confirm that the old version can read the current data.

If only the image changed, run:

```sh
kubectl -n zeabur-identity set image deployment/zeabur-identity zeabur-identity="$PREVIOUS_IMAGE"
```

If the Pod template has other changes, inspect the revision history first:

```sh
kubectl rollout history deployment/zeabur-identity --revision=N
```

Then roll back to the specified revision:

```sh
kubectl rollout undo deployment/zeabur-identity --to-revision=N
```

Manually revert the other changes, then restore the replica count.

#### You can't confirm that the old version can read the current data

Follow the restore procedure in [Backup and restore](./backup-restore.mdx) to restore the pre-upgrade backup, along with the old image, manifests, CRDs, and Secrets. Keep Zeabur Identity stopped throughout the restore.

You'll lose all changes made after the backup, including new passkeys, group changes, client updates, and key rotations.

<Callout type="warn">

Restoring a backup brings back revoked sessions and used invitations that the backup contains. Delete these sessions and invitations before reopening the service.

</Callout>

Don't install an empty signing-key Secret, delete certificates, or issue new setup links to get the old version running.

</Step>

<Step>

### Verify the rollback and record data loss

Check the image, readiness, and logs, then sign in again. Confirm that regular access, admin access, and emergency access all work.

Record what you restored and what data you lost.

</Step>

</Steps>
