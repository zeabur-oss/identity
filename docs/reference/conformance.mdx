---
title: Specification conformance
description: Which standards Zeabur Identity follows, which guarantees it adds, and what it does not do.
---

Zeabur Identity lets Kubernetes users sign in with a passkey, a password or an upstream account. It then issues tokens that kube-apiserver verifies. It follows OAuth 2.0 and OpenID Connect, and it follows WebAuthn and Kubernetes Structured Authentication Configuration. This page says what it does, what it does not do, and why.

Zeabur Identity is not OpenID Certified. The OpenID Foundation `oidcc-basic-certification-test-plan` ran once on v0.3.4, but the result is not a certification. The plan sends no `code_challenge`, and Zeabur Identity always requires PKCE, so the run used a build with PKCE made optional. The other failed cases come from the missing single sign-on (SSO) session: `prompt=none` while signed in, `id_token_hint` and `max_age`.

Every requirement has an automated test. The whole flow is checked on a real k3s cluster and with Keycloak.

Specification numbers are in the footnotes. Maintainers keep the row-by-row list of code and tests in `docs/internal/conformance.md` in the repository.

## What kube-apiserver needs to verify tokens

kube-apiserver finds the signing keys in the discovery document, then uses them to verify every access token. The document and the keys must therefore be right.

- The discovery document is served at both the OpenID Connect and the OAuth standard locations. The two documents are identical, and `issuer` matches[^discovery].
- Tokens use only ES256 and RS256. A key is used for one algorithm. The server accepts no `jku` or `x5u` header, which let an attacker choose the key source, and no `none` algorithm[^jose].
- A new key is published for a while before it signs, and a retired key stays published for a while. A key change therefore does not break the kube-apiserver cache[^rotation].
- Access tokens use the `at+jwt` type, with a separate `aud` for each resource[^jwt-at].
- CI runs `kubectl auth whoami` on k3s every time. RKE2 v1.36.5+rke2r1 was checked by hand[^kep].

## The sign-in flow

The authorization code flow is the only flow, with several extra restrictions.

- PKCE is required, and only S256 is accepted[^pkce].
- A redirect URI must match exactly. Only the port of a loopback address may differ. When an authorization request is wrong, the server shows an error page and never redirects to an address it cannot trust[^redirect].
- An authorization code works once. If a code is used again, the tokens it already issued are revoked[^code].
- A refresh token is replaced at each use. When an old token appears again, it was stolen, and the whole refresh family is revoked[^refresh].
- Authorization responses carry `iss`, which stops mix-up attacks[^iss].
- Pushed authorization requests and token revocation are supported[^par].
- Every authorization request asks for a new sign-in, because there is no SSO session. `max_age` and `prompt=login` are therefore always met[^core].

## Ways to sign in

The sign-in page offers a passkey, a password and an upstream account. A regular account can use any of them.

- Passkeys use WebAuthn. They must be discoverable and need user verification (fingerprint, face or PIN). Browser autofill is supported[^webauthn].
- A password sign-in gives the same answer for an unknown user, a wrong password and a blocked browser. Wrong attempts are counted for each browser. The sign-in can ask for a code from an authenticator app. Each code and each recovery code works once[^totp].
- The first admin exists only through a one-time setup link. There is no "first visitor becomes admin". A link works once and expires.
- An invitation works once and only for the invited user. The service account cannot create invitations.
- Setup links and invitations are bound to the user's UID. If a user is deleted and a new user gets the same name, the old links, codes and refresh tokens do not apply to the new user.
- The sign-in pages have no inline script or style, send headers against clickjacking, and never put tokens in browser storage[^csp].

## Accounts, admins and sessions

Accounts are either admin or regular. The `admin-sign-in` setting limits how admins sign in.

- `two-factor` (default): an admin uses a passkey, or a password with a code or recovery code from an authenticator app, or an OpenID provider marked `mfa: Enforced`.
- `any`: admins sign in like regular accounts.
- `passkey`: a passkey only.
- `device-bound-passkey`: a device-bound passkey only. A synced passkey can neither sign in nor be enrolled.
- Unless `admin-sign-in` is `any`, admins cannot sign in with or link a provider that is not marked `mfa: Enforced`, such as GitHub or Google. The mark is the operator's statement. Zeabur Identity does not read the `amr` that the provider reports.
- The server checks this limit at sign-in, at code exchange and at every refresh. A session that no longer qualifies ends at its next refresh.
- Only admin tokens carry the `admins` group, and they are shorter (5 minutes, against 10 for a regular account). The CRD does not allow `admins` in `spec.groups`.
- A refresh session ends after 1 hour idle, or 15 minutes for an admin with several teams or with `device-bound-passkey`. Every session ends 12 hours after sign-in. These limits follow NIST SP 800-63B-4 AAL2[^nist].
- The first admin is bound to `cluster-admin` and needs no second sign-in. A refresh follows the account type, so a regular account keeps no admin rights.

## The account page

Users manage their passkeys, password and linked upstream accounts at `/account`.

- Every read and write is limited to the signed-in user. Names in a request only choose among that user's own items.
- Before a user adds or removes a passkey, or links or unlinks an upstream account, the user must verify again with a passkey within the last five minutes[^reauth].
- Changing or removing a password needs the current password. Wrong attempts share the limits of sign-in. After a change or removal, the user's other sessions end.
- The last way to sign in can never be removed, even when several removals run at the same time.
- Removing a passkey revokes the sessions and grants that it signed in.
- Every change leaves an audit log line and an `Event` on the `User`. They record the actor, the credential, the device model, the IP address and the browser.
- The account page publishes `/.well-known/passkey-endpoints`, so browsers and password managers can find the enrol and manage pages[^passkey-endpoints].

## Upstream sign-in (GitHub and OpenID providers)

An upstream account signs in only to an account that is already linked. It never creates a user.

- A link is made only through a setup link, an invitation, or the account page of a signed-in user. Linking from the account page needs a fresh passkey verification.
- One upstream account cannot link to two users.
- At sign-in the server checks `state`, PKCE and `iss`, and in the ID token the signature, `iss`, `aud`, `azp`, `exp` and `nonce`[^upstream].
- A new, changed or deleted provider, and a rotated client secret, apply at the next request with no restart. Deleting a provider does not delete the accounts linked through it.
- The whole flow was checked with a real Keycloak. An unlinked account is refused, a linked account signs in, and an unlinked account is refused again.

## Storage and permissions

All data is in Kubernetes custom resources. There is no other database.

- Every "only once" action (authorization code, setup link, refresh rotation) uses a Kubernetes `resourceVersion` compare-and-swap. A cluster test sends 64 requests at once and checks that exactly one succeeds.
- The service account has least privilege. It reads a Secret only by name, cannot create Secrets and has no RBAC verbs.
- A redirect URI is checked by CRD admission and by `zeabur-identityctl client create`. Only `https://` and a loopback `http://` with a path are accepted.
- A generated client secret is 256 random bits, and only its hash is stored[^secret].
- A background task deletes expired objects.

## What it does not do

- **SSO sessions and logout.** There is no SSO session, so there is no RP-Initiated Logout and no Back-Channel Logout[^logout].
- **DPoP.** kube-apiserver accepts only bearer tokens, so DPoP would add nothing[^dpop].
- **Rich Authorization Requests and step-up authentication.** kube-apiserver cannot evaluate `authorization_details` and never sends a step-up challenge. Admin rights come from a separate admin account instead, and `admin-sign-in` limits how it signs in.
- **`ui_locales`.** The sign-in page picks its language from `Accept-Language` and ignores this parameter.
- **Accessibility audit.** The contrast of every color pair is computed and meets WCAG 2.2 AA. There is no automated browser audit and no screen-reader pass yet[^wcag].
- **Proof of AAL3.** `device-bound-passkey` relies on what the passkey reports about itself. Attestation is `none`.

## How it is checked

Every guarantee has a test, and the maintainer list names each one. There are three kinds of test:

- Unit and integration tests run in every CI run.
- Cluster tests use k3s `v1.37.2` and run in every CI run.
- End-to-end tests use the Zeabur Identity container image. The Keycloak test needs its own server. Run it with `scripts/keycloak-e2e.sh`. It does not run in CI.

For the supply-chain and build requirements, such as no `unsafe`, OSI licenses only, a non-root image without a shell, and image signing with an SBOM, see [Security](security.mdx) and [Releases](releases.mdx). For design decisions, see [Architecture](architecture.mdx).
