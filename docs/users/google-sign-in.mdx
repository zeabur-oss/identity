---
title: Let users sign in with Google
description: Configure a Google OAuth client and link user accounts so regular accounts can sign in to Zeabur Identity with Google.
---

Configure a Google OAuth client, then link Google accounts to Zeabur Identity users. Users can then select **Continue with Google** on the sign-in page. Admin accounts can only sign in with passkeys and can't link Google accounts.

## Before you begin

- Install Zeabur Identity in the `zeabur-identity` Namespace, and run `zeabur-identityctl` and `kubectl` with a cluster administrator's kubeconfig.
- Have a real public domain ready. Google only accepts redirect URIs on public domains. See [Google's URI validation rules](https://developers.google.com/identity/protocols/oauth2/web-server#uri-validation). The local name `identity.example.test` used in [Install and sign in on k3s](../get-started/quickstart.mdx) won't work.
- Confirm that your browser can reach Zeabur Identity at that domain and trusts its TLS certificate.
- Confirm that the Zeabur Identity Pod can make outbound HTTPS connections to `oauth2.googleapis.com` and `www.googleapis.com`.

The examples below use `https://identity.example.com`. Replace each example with the Issuer you configured during installation:

```sh
export ZEABUR_IDENTITY_ISSUER=https://identity.example.com
```

Installation fixes the Issuer. The Zeabur Identity Deployment, TLS certificate, and kube-apiserver configuration must use the same name. Changing `ZEABUR_IDENTITY_ISSUER` in your shell afterward doesn't change the Issuer of an existing installation.

Users must link their Google accounts to Zeabur Identity users before they can sign in. Zeabur Identity doesn't create users on first sign-in or match accounts by email address, name, or Workspace domain. Groups and display names come from `User`.

## Configure Google sign-in

<Steps>

<Step>

### Register a Google OAuth client

Follow Google's [OpenID Connect setup documentation](https://developers.google.com/identity/openid-connect/openid-connect) and [consent screen configuration guide](https://developers.google.com/workspace/guides/configure-oauth-consent) to complete these settings in Google Cloud Console:

1. Select or create a project. Under **Google Auth platform → Branding**, set the application name, support email, and contact information.
2. Under **Audience**, select **Internal** to restrict access to your Google Workspace organization, or select **External** to accept any Google account. Both settings require users to link their Zeabur Identity accounts first. [Google's publishing rules](https://support.google.com/cloud/answer/15549945) restrict applications in testing mode, but applications that only request `openid`, such as Zeabur Identity, are exempt.
3. Under **Data Access**, declare only the `openid` scope. No Google API data access is required.
4. Under **Clients → Create Client**, select **Web application**, set a name, and add the following URI under **Authorized redirect URI**. Replace the domain with your Issuer:

   ```text
   https://identity.example.com/upstream/google/callback
   ```

   The URI must match `<issuer>/upstream/google/callback` exactly. Leave **Authorized JavaScript origins** empty.
5. Save the **Client ID** and **client secret**. Zeabur Identity needs the client secret itself, not the JSON file Google offers for download.

</Step>

<Step>

### Store the client secret and enable Google sign-in

Zeabur Identity reads secrets from Kubernetes Secret files mounted at `/etc/zeabur-identity`. Run the following commands to keep the secret out of your shell history and process list:

```sh
read -rs GOOGLE_SECRET     # paste the client secret, then Enter
printf %s "$GOOGLE_SECRET" | kubectl -n zeabur-identity create secret generic zeabur-identity-config \
  --from-file=google-client-secret=/dev/stdin
unset GOOGLE_SECRET
```

If `zeabur-identity-config` already exists, for example, because it stores the secret for [Sign in with GitHub](./github-sign-in.mdx), add the `google-client-secret` key to the existing Secret. Use a secret management tool, or run the following command to edit the Secret. Its values use base64 encoding:

```sh
kubectl -n zeabur-identity edit secret zeabur-identity-config
```

Next, regenerate the Deployment with the Secret and the two Google options. `zeabur-identityctl manifests` doesn't remember previous options. Keep all the settings you used during installation, including the image, Namespace, and other `--serve-arg` options. Keep `--invitations` as well; the next step needs it.

```sh
GOOGLE_CLIENT_ID=1234567890-example.apps.googleusercontent.com   # replace with your client ID
ZEABUR_IDENTITY_IMAGE=$(kubectl -n zeabur-identity get deployment zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].image}')
zeabur-identityctl manifests --image "$ZEABUR_IDENTITY_IMAGE" \
  --config-secret zeabur-identity-config \
  --serve-arg=--invitations \
  --serve-arg=--google-client-id=$GOOGLE_CLIENT_ID \
  --serve-arg=--google-client-secret-file=/etc/zeabur-identity/google-client-secret \
  | kubectl apply --server-side -f -
kubectl -n zeabur-identity rollout status deploy/zeabur-identity
```

After the rollout finishes, the sign-in page displays **Continue with Google**.

</Step>

<Step>

### Link Google accounts

Choose a linking method based on the user's current status:

- A regular account that can already sign in: Open the account page, verify your identity with a passkey, and select **Link Google**. See [Manage users](./manage-users.mdx) for account page instructions.
- A new user: Send an invitation as described in [Manage users](./manage-users.mdx).
- An existing user who can't sign in yet: Send another invitation with the same username. If the user already has a passkey or linked account, the invitation requires `--reset`, which first deletes existing passkeys and linked accounts. See [Sign out, recover, and remove users](./offboarding.mdx) for the recovery procedure.

After opening the setup link, the user selects **Continue with Google**, then chooses the Google account to use.

<Callout type="warn">

Anyone with the setup link can control that Zeabur Identity user. Give the link to the correct person. Each setup link can add only one passkey or one account. A Google account can link to only one user at a time.

</Callout>

Admin accounts can't link Google accounts. Even if the Google account has two-factor authentication enabled, admins can only sign in with passkeys. See [Admin accounts and sessions](./admin-sessions.mdx).

</Step>

</Steps>

## Verify the result

If you use the `kubectl` configuration from [Install and sign in on k3s](../get-started/quickstart.mdx), clear the cached session first so kubelogin opens the browser again:

```sh
rm -rf ~/.kube/cache/oidc-login
kubectl auth whoami          # choose "Continue with Google"
```

Select **Continue with Google** on the sign-in page, sign in with a linked regular account, and check the identity that `kubectl auth whoami` displays. Don't use admin accounts such as `admin` from the quickstart. These accounts don't accept Google sign-in.

### Remove a user's access

A linked Google account is a `Credential`, like a passkey. Remove that credential as described in [Manage users](./manage-users.mdx) to prevent the user from signing in again with that Google account.

To end existing sessions, you also need to sign the user out. To revoke all access, disable or remove the user. See [Sign out, recover, and remove users](./offboarding.mdx).

### Rotate the client secret

Zeabur Identity reads the client secret only at startup. After updating the Secret, restart Zeabur Identity:

```sh
kubectl -n zeabur-identity rollout restart deploy/zeabur-identity
kubectl -n zeabur-identity rollout status deploy/zeabur-identity
```

### Disable Google sign-in

Regenerate the Deployment without the two `--google-*` options, and keep the other options. If you no longer need the OAuth client, delete it in Google Cloud Console as well.

Disabling Google sign-in doesn't remove linked accounts or end existing sessions. To revoke access, follow the procedure above to remove credentials and sign the user out.

## Troubleshooting

| Screen or result | What to do next |
| --- | --- |
| `redirect_uri_mismatch` | Check the client ID and authorized redirect URI. The scheme, hostname, and `/upstream/google/callback` must match exactly. Local names such as `identity.example.test` don't meet Google's domain rules. |
| `org_internal` or a Google access policy error | Check the application's **Audience** and the policies of the account's organization. See [Google's audience rules](https://support.google.com/cloud/answer/15549945). |
| **This account is not linked to any user here** | Use an invitation to link the selected Google account to a user. Zeabur Identity doesn't match accounts by email address or name. |
| **Use a passkey for this account** | The Google account maps to an admin account. Admins can only sign in with passkeys. |
| No Google button on the sign-in page, or the Pod can't read the secret | Check the two `--google-*` options, `--config-secret zeabur-identity-config`, the `google-client-secret` key in the Secret, and the file path. If you customized the Pod's security context, keep the generated `fsGroup`. |
| Sign-in fails after returning from Google | Run `kubectl -n zeabur-identity logs deploy/zeabur-identity` to view the logs, and check whether the Pod can reach the token and signing key hosts over HTTPS: `oauth2.googleapis.com` and `www.googleapis.com`. |
