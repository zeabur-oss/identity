---
title: Let users sign in with GitHub
description: Enable GitHub sign-in and link regular accounts so users can access the cluster with their GitHub accounts.
---

After you enable GitHub sign-in in Zeabur Identity and link GitHub accounts to regular accounts, users can select **Continue with GitHub** on the sign-in page to sign in with GitHub.

![Sign-in page with a passkey button and Continue with GitHub](../images/sign-in-light.avif)

You decide who can sign in. Unlinked GitHub accounts can't sign in, and Zeabur Identity won't create users for them. GitHub organizations and teams don't affect access permissions; `User` still determines group membership. Zeabur Identity records GitHub's numeric account ID so that transferring a login name or email address to someone else doesn't affect account identification.

## Before you begin

- Complete [Install and sign in on k3s](../get-started/quickstart.mdx).
- Run the installation commands in the server's `nix develop` environment, and replace the Issuer below with your URL.
- Confirm that the cluster lets Zeabur Identity Pods make outbound HTTPS connections to `github.com` and `api.github.com`.
- Prepare the regular accounts you want to link. [Admin accounts](./admin-sessions.mdx) can only sign in with passkeys and can't link GitHub accounts.

```sh
export ZEABUR_IDENTITY_ISSUER=https://identity.example.test
```

## Enable GitHub sign-in

<Steps>

<Step>

### Register a GitHub OAuth application

In GitHub, open **Settings → Developer settings → OAuth Apps → New OAuth App**. You can also register the application in your organization settings so it doesn't depend on a personal account.

| Field | Value |
|---|---|
| **Application name** | For example, `Zeabur Identity (zeabur-identity-k3s)`. Users will see this name on GitHub's authorization page |
| **Homepage URL** | `https://identity.example.test` |
| **Authorization callback URL** | `https://identity.example.test/upstream/github/callback` |
| **Enable Device Flow** | Off |

Replace the URLs with your Issuer. The callback URL only redirects the browser.

After registration, record the **Client ID** and generate a **client secret**.

</Step>

<Step>

### Store the client secret

Zeabur Identity reads the secret from a file in a Kubernetes Secret mounted at `/etc/zeabur-identity`.

Run the following commands to keep the secret out of your shell history and process list:

```sh
read -rs GITHUB_SECRET     # paste the client secret, then Enter
printf %s "$GITHUB_SECRET" | kubectl -n zeabur-identity create secret generic zeabur-identity-config \
  --from-file=github-client-secret=/dev/stdin
unset GITHUB_SECRET
```

If `zeabur-identity-config` already exists, for example, to store the [Google sign-in](./google-sign-in.mdx) secret, use the following command to add the key and preserve the other keys:

```sh
kubectl -n zeabur-identity edit secret zeabur-identity-config
```

</Step>

<Step>

### Enable the GitHub sign-in provider

Regenerate the deployment configuration with the Secret and Client ID.

`zeabur-identityctl manifests` doesn't remember previous options. Keep the image, Namespace, and other `--serve-arg` options from your installation, and add the GitHub options.

The following commands reuse the configuration from [Install and sign in on k3s](../get-started/quickstart.mdx), including `--invitations`, which you'll need to invite users in the next step. Replace `GITHUB_CLIENT_ID` with the **Client ID** you obtained earlier; this value isn't a secret.

```sh
GITHUB_CLIENT_ID=Ov23li...   # from step 1; not a secret
ZEABUR_IDENTITY_IMAGE=$(kubectl -n zeabur-identity get deployment zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].image}')
zeabur-identityctl manifests --image "$ZEABUR_IDENTITY_IMAGE" \
  --config-secret zeabur-identity-config \
  --serve-arg=--invitations \
  --serve-arg=--github-client-id=$GITHUB_CLIENT_ID \
  --serve-arg=--github-client-secret-file=/etc/zeabur-identity/github-client-secret \
  | kubectl apply --server-side -f -
kubectl -n zeabur-identity rollout status deploy/zeabur-identity
```

After the deployment completes, the sign-in page displays **Continue with GitHub**.

</Step>

<Step>

### Link a GitHub account to a user

Choose a linking method based on the user's current status:

- Users who can already sign in: Open the account page, verify their identity with a passkey, and select **Link GitHub**. Admin accounts can't link GitHub accounts.
- New users: Create an invitation as described in [Manage users](./manage-users.mdx).
- Users who have an account but can't sign in yet: Create another invitation with the same username. If the account already has a passkey or a linked account, add `--reset` to the invitation command. For account recovery instructions, see [Sign out, recover, and remove users](./offboarding.mdx).

After opening the invitation link, the user selects **Continue with GitHub** without creating a passkey, then signs in to the GitHub account they want to link. Each link can add only one passkey or one account.

<Callout type="warn">

`--reset` first deletes the user's existing passkeys and linked accounts.

</Callout>

#### Advanced: Create a Credential directly without a link

If you know the user's GitHub login name, you can also create a `Credential` directly. The object must meet the following requirements:

- Derive `metadata.name` from GitHub's numeric account ID. Zeabur Identity looks up accounts by this name.
- Include the user label so the commands in [Manage users](./manage-users.mdx) can find the credential.
- Point `ownerReferences` to the `User` that owns the sign-in identity, and include that `User`'s UID. When you delete the user, Kubernetes also deletes the credential.

The GitHub account can't sign in if `ownerReferences` is missing or the UID points to another `User`.

Replace `LOGIN` with the GitHub login name and `USER_NAME` with the name of an existing `User`:

```sh
LOGIN=octocat
USER_NAME=alice                                   # an existing User object
USER_UID=$(kubectl -n zeabur-identity get users.identity.zeabur.com "$USER_NAME" -o jsonpath='{.metadata.uid}')
GH_ID=$(curl -fsS https://api.github.com/users/$LOGIN | jq -r .id)
NAME=c-$(printf 'zeabur-identity/external/v1/https://github.com\0%s' "$GH_ID" | sha256sum | cut -d' ' -f1)
kubectl apply -f - <<EOF
apiVersion: identity.zeabur.com/v1alpha1
kind: Credential
metadata:
  name: $NAME
  namespace: zeabur-identity
  labels: {identity.zeabur.com/user: "$USER_NAME"}
  ownerReferences:
    - {apiVersion: identity.zeabur.com/v1alpha1, kind: User, name: $USER_NAME, uid: $USER_UID}
spec:
  type: GitHub
  user: $USER_NAME
  external: {issuer: "https://github.com", subject: "$GH_ID"}
EOF
```

<Callout type="warn">

Check `$GH_ID` before running `kubectl apply`. An incorrect ID links someone else's GitHub account.

</Callout>

</Step>

</Steps>

## Verify the result

Clear the cached session on your computer so kubelogin opens the browser again. Run the following commands, then select **Continue with GitHub**:

```sh
rm -rf ~/.kube/cache/oidc-login
export KUBECONFIG=~/.kube/zeabur-identity-k3s.yaml
kubectl auth whoami          # choose "Continue with GitHub"; the user is zeabur:<username>
```

Confirm that `kubectl auth whoami` shows the user as `zeabur:<username>`.

You can also identify the sign-in method from `identity.zeabur.com/amr` in the output:

- Passkey sign-ins list `swk` and `mfa`.
- GitHub sign-ins leave it empty.

Use a regular account for verification. Admin accounts, such as the `admin` account created in the quickstart, don't accept GitHub sign-ins.

## Remove GitHub sign-in access

Linked GitHub accounts are `Credential` objects, like passkeys:

- Remove a linked account to stop new sign-ins with that account. See [Manage users](./manage-users.mdx).
- Sign the user out to end existing sessions. See [Sign out, recover, and remove users](./offboarding.mdx).
- Disable or remove the user to revoke all access. See [Sign out, recover, and remove users](./offboarding.mdx).

To turn off GitHub sign-in, regenerate the deployment configuration without the two `--github-*` options, keep the other options, and delete the OAuth application in GitHub. Linked accounts and existing sessions remain; remove them as described above.

## Troubleshooting

| Screen or result | Next action |
|---|---|
| GitHub reports that the redirect URI doesn't belong to this application | Confirm that the OAuth application's callback URL exactly matches `<issuer>/upstream/github/callback`. |
| **This account is not linked to any user here** | The GitHub account has no matching `Credential`. Follow the account-linking steps. A manually created credential with an incorrect name or ID also produces this message. |
| **Use a passkey for this account** | The GitHub account links to an admin account. Admin accounts can only sign in with passkeys. |
| **This provider is not enabled** | The Deployment is missing `--github-client-id`. Run `kubectl -n zeabur-identity get deploy zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].args}'` to check the arguments. |
| The Pod can't read `/etc/zeabur-identity/...` | Confirm that `--config-secret zeabur-identity-config` mounts the Secret, the Secret contains `github-client-secret`, and `--github-client-secret-file` points to `/etc/zeabur-identity/github-client-secret`. If you customize the Pod's security settings or mounts, preserve `fsGroup` and the read permissions from the generated configuration. |
| Sign-in fails after GitHub redirects back | The Pod can't connect to `github.com` or `api.github.com`. Check outbound connection settings, including proxies, firewalls, and NetworkPolicy, and run `kubectl -n zeabur-identity logs deploy/zeabur-identity` to view the logs. |
