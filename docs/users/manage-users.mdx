title: Add and manage users
description: Invite users to set up passkeys, update groups and display names, and manage passkeys and linked accounts.

Use `zeabur-identityctl` to invite users to set up passkeys, then use `kubectl` to manage groups and accounts. After signing in, users can add or remove passkeys, link accounts, and end sessions on their account page.

![Setup page: Create a passkey with a one-time link](../images/setup-light.avif)

## Before you begin

- Have `zeabur-identityctl` ready to create one-time setup links.
- Have `kubectl` or a GitOps tool ready to manage groups, admin accounts, sign-outs, and user removal.
- Run commands in an environment with a cluster admin kubeconfig.

The following examples use the environment from [Install and sign in on k3s](../get-started/quickstart.mdx), with Namespace `zeabur-identity` and Issuer `https://identity.example.test`. Set the environment variable to your own Issuer:

```sh
export ZEABUR_IDENTITY_ISSUER=https://identity.example.test
```

`zeabur-identityctl` reads `ZEABUR_IDENTITY_ISSUER`, so you don't need to specify it again in later commands.

### User-related objects

Zeabur Identity stores users, passkeys, and sessions as Kubernetes objects in its own Namespace.

| Object | Short name | Purpose | Created by |
|---|---|---|---|
| `User` | `zbuser` | A user, including their username, display name, groups, and account type | You |
| `Credential` | `zbcred` | A passkey or a linked GitHub, Google or OpenID Connect account | Zeabur Identity, when the user uses a link |
| `Invitation` | `zbinvite` | An unused one-time link | `zeabur-identityctl invite`; Zeabur Identity deletes it after the link is used or expires |
| `Grant` | `zbgrant` | A signed-in session: applications use `g-…`, and the account page uses `s-…` | Zeabur Identity, at each sign-in |

`Credential`, `Invitation`, and `Grant` all carry the label `identity.zeabur.com/user=<username>`. Use `-l identity.zeabur.com/user=alice` to select these objects for `alice`.

By default, tokens for regular accounts expire after 10 minutes, and tokens for admin accounts expire after 5 minutes. For session settings, see [Admin accounts and sessions](./admin-sessions.mdx).

## Invite a new user

<Steps>

<Step>

### Create the user and setup link

```sh
zeabur-identityctl invite --username alice --display-name "Alice Chen" --group dev
```

This command creates the user `alice`, adds her to the `dev` group, and outputs a one-time setup link. To add multiple groups, repeat `--group`.

The link expires after 7 days. You can't extend its lifetime. To shorten it, specify `--valid-for 24h`.

`--group`, `--admin`, and `--display-name` only configure new users. Inviting an existing user only adds a passkey or links a GitHub, Google or OpenID Connect account; it doesn't change their groups or display name.

If the user already has a passkey or linked account, `invite` reports an error and stops. `--reset` deletes these sign-in credentials first. For account recovery, see [Sign out, recover, and remove users](./offboarding.mdx).

</Step>

<Step>

### Give the link to the user

Send the link to Alice through a channel you trust. She can open the link to create a passkey. If you've enabled [Sign in with GitHub](./github-sign-in.mdx) or [Sign in with Google](./google-sign-in.mdx), she can also link the corresponding account.

<Callout type="warn">

Until someone uses the link or it expires, anyone who has it can become Alice. Give the link only to her.

</Callout>

Zeabur Identity doesn't send email. The command outputs the link to stdout and other messages to stderr. You can send the link with a script:

```sh
link=$(zeabur-identityctl invite --username alice --group dev)
mail -s "Set up your passkey" alice@example.com <<EOF
Open this link on the device that will keep your passkey:

$link
EOF
```

Zeabur Identity records events on the `User` when it issues an invitation and when someone uses it: `InvitationIssued` and `InvitationRedeemed`, respectively. Check the events to see when and where someone used the link:

```sh
kubectl -n zeabur-identity get events --field-selector involvedObject.name=alice
```

</Step>

<Step>

### Grant permissions to the group

Kubernetes identifies Alice as user `zeabur:alice`, with group `zeabur:dev`. Grant permissions to groups rather than individual users.

The following example grants the `dev` group permission to edit all resources in the `dev` Namespace:

```sh
kubectl create namespace dev            # if it does not exist yet
kubectl create rolebinding dev-edit --clusterrole=edit --group=zeabur:dev -n dev
```

</Step>

</Steps>

## When a link doesn't work

### Check that the server has invitations enabled

Invitation links require the server to enable `--invitations`. [Install and sign in on k3s](../get-started/quickstart.mdx) enables this option. If your installation doesn't have it enabled, add the option and regenerate the deployment configuration:

```sh
ZEABUR_IDENTITY_IMAGE=$(kubectl -n zeabur-identity get deployment zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].image}')
zeabur-identityctl manifests --image "$ZEABUR_IDENTITY_IMAGE" \
  --serve-arg=--invitations | kubectl apply --server-side -f -
kubectl -n zeabur-identity rollout status deploy/zeabur-identity
```

<Callout type="warn">

`zeabur-identityctl manifests` doesn't remember previous options. Before running it, include the image, Namespace, `--config-secret`, and all `--serve-arg` options from your installation, then add `--serve-arg=--invitations`.

</Callout>

### Check that the user isn't disabled

Invitation links don't work while a user is disabled. After you re-enable the user, the same link works again as long as it hasn't expired:

```sh
kubectl -n zeabur-identity patch zbuser alice --type=merge -p '{"spec":{"disabled":false}}'
```

## Change groups and display names

Edit the user's `User` object. The following command changes `alice`'s groups to `dev` and `oncall`:

```sh
kubectl -n zeabur-identity patch zbuser alice --type=merge -p '{"spec":{"groups":["dev","oncall"]}}'
```

Group changes appear in the next token Zeabur Identity issues. Existing tokens retain the old groups until they expire; tokens that `kubectl` uses expire within 10 minutes.

Read back the groups first. Then ask the user to sign in again and use their own kubeconfig to check the identity that kube-apiserver sees:

```sh
kubectl -n zeabur-identity get zbuser alice -o jsonpath='{.spec.groups}'
kubectl auth whoami          # Groups lists zeabur:dev and zeabur:oncall
```

If the user has the label `identity.zeabur.com/source=directory`, directory sync manages the account. Change the display name and groups in the directory. See [Sync users from a directory](./provisioning.mdx).

`groups` doesn't accept the `admins` group. Only the account type determines membership in this group. See [Admin accounts and sessions](./admin-sessions.mdx).

You can't change a username because RBAC bindings and audit records reference it. To change a username, create a new user, then [remove the old user](./offboarding.mdx).

## Let users manage their accounts

Users can open `https://<issuer>/account` to manage their passkeys and sessions:

- Add, rename, or remove passkeys.
- View and end sessions.
- Link or unlink GitHub, Google or OpenID Connect accounts for regular accounts, after you enable the corresponding sign-in option.

Users must verify their identity with a passkey before adding a passkey, linking an account, or removing a credential. Users can't remove their last passkey or unlink their last account available for sign-in on the account page.

When a user removes a passkey or unlinks an account on the account page, Zeabur Identity also ends all sessions that used that credential to sign in. Each change produces a log entry and an event on the `User`:

```sh
kubectl -n zeabur-identity get events --field-selector involvedObject.name=alice
```

Account page sessions expire after 1 hour. Password managers find the account page through `/.well-known/passkey-endpoints`.

### Add a passkey or device

Most passkeys sync through platform accounts, such as iCloud Keychain or Google Password Manager, so switching to a new phone usually doesn't require extra setup. To use a separate security key, users can add it on the account page.

Regular accounts can also link GitHub, Google or OpenID Connect accounts on the account page. The same external account can't link to different users at the same time. To link it to another user, unlink it on the original user's account page first. Admin accounts can't link external accounts.

Don't use `invite` to add passkeys or link accounts for users who can already sign in. If the link reaches the wrong person, that person can sign in as the user. If the user can no longer sign in, follow the recovery process in [Sign out, recover, and remove users](./offboarding.mdx).

### Remove passkeys or linked accounts as an admin

Admins can also list and delete `Credential` objects directly:

```sh
kubectl -n zeabur-identity get zbcred -l identity.zeabur.com/user=alice
kubectl -n zeabur-identity delete zbcred <name>
```

After deletion, the credential can no longer sign in. Deleting a `Credential` directly doesn't end sessions it previously created; those sessions remain usable. Follow [Sign out, recover, and remove users](./offboarding.mdx) to sign the user out. Removing a credential on the account page also ends the associated sessions.
